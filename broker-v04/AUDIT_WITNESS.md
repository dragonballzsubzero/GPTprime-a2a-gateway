# Audit checkpoint witness candidate

The witness reads an internally consistent ledger snapshot and signed head using a reader credential distinct from the append credential. It verifies every record's sequence, predecessor, signed acknowledgement and signed chain link, checks duplicate events and result-to-intent ordering, and checks that the previous retained head appears in the new history. It writes a complete checkpoint using a no-overwrite filesystem link after syncing the file, then syncs the containing directory. A process restart validates all retained checkpoints and requires the latest signed head from a separately retained source. Alteration, a signed fork, a rollback, or loss of the latest anchored file fails closed.

This is **not an operated or immutable external audit service**. The audit source and witness require distinct operator identities, machines, credentials and storage. Neither a signature nor two processes establishes that separation. The retention directory needs a durable, separately administered volume and an independently retained, current head; its administrator can otherwise delete or replace files, and an attacker who can roll back both the directory and the external head can hide that rollback. A stale head cannot detect deletion after that head. A fixed retention period, backup restore procedure, independent monitoring and a remote immutable storage provider remain to be commissioned and tested. No production storage or secret is created here.

For storage research, [Amazon S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html) provides version retention modes; compliance retention has irreversible consequences during its retention period and needs an appropriately scoped account and deliberate duration. The connected [Vercel Blob](https://vercel.com/docs/vercel-blob/security) read/write token can read and write; the platform also supports deleting blobs, so a private Blob store by itself is not a WORM witness. Selecting a provider and retention period is an operational decision, not an assertion made by the test suite.

## Running the candidate

1. Provision a dedicated private witness directory, service identity, TLS/mTLS boundary and durable storage. Install a trusted copy of the auditor's public JWK and ID out of band. The directory and checkpoint files must be owned by the witness user and inaccessible to group and others. Do not place private signing keys on the witness.
2. On the audit service, set `SAC_AUDIT_READER_TOKEN_PATH` to a private file containing a distinct random reader token. The audit process exposes `/snapshot` only when this is configured. The reader token cannot call `/append` or `/head`; the append token cannot call `/snapshot`. The shipped HTTP server binds loopback only, so an independently managed authenticated transport is still required.
3. Configure `SAC_WITNESS_DIR`, `SAC_AUDIT_ORIGIN` (HTTPS origin only), `SAC_AUDIT_READER_TOKEN_PATH`, `SAC_AUDIT_SINK_ID` and `SAC_AUDIT_PUBLIC_JWK_PATH`. For an explicitly verified empty directory, set `SAC_WITNESS_BOOTSTRAP=1` once. Run `node broker-v04/witness-main.mjs` and retain the signed head it prints through a separate trusted storage/operator boundary.
4. For each subsequent run, remove the bootstrap setting and set `SAC_WITNESS_EXPECTED_HEAD_PATH` to the most recent externally retained signed head. After every successful checkpoint, retain the newly printed head before the next restart. If the head and retained directory disagree, stop and investigate; do not bootstrap over existing history or automatically discard a checkpoint.

The witness keeps a complete snapshot per changed head; storage and verification cost therefore increase with checkpoint frequency and total ledger size. The source log is capped at 64 MiB, and the witness has no automatic rotation or retention deletion. Full-disk conditions, interrupted publication, or stale writer locks require investigation and fail closed. A leftover `.pending-*` file is not automatically removed. Because a crash can occur after a checkpoint is published but before its head is independently retained, manual reconciliation may be required. Test those cases on the actual host and storage implementation before relying on this code.
