# Model-independent execution broker v0.4 — review candidate

**Status: the v0.4 database function is installed but locked; the broker runtime is not deployed or production-qualified.** See `LIVE_INSTALL_2026-11-15.md` for the migration and readback. This is additive to `broker-v03` and does not enable `api/dispatch.js`. The only candidate effect is the existing database-only `audit_canary`; arbitrary shell, network, file, repository and provider effects are not exposed.

## Flow

1. An independently enrolled adapter proposes a narrowly defined action. Its host-controlled signer signs the v0.3 node-proposal domain; the model supplies no key. `proposal-client.mjs` accepts an injected signing function and checks the result against the trusted node public key.
2. The broker authenticates the caller using Supabase Auth, requires signed AAL2 claims and the existing database owner/session/MFA-factor gate, checks node/owner trust, verifies the node signature and stores the proposal. Node names are not hardcoded to a model provider.
3. On a trusted owner machine, `owner-approve.mjs` displays the validated proposal and requires the owner to type `APPROVE ` followed by its exact action digest in a terminal. It creates a short-lived v0.4 grant bound to owner, node, run, action digest, proposal, nonce, both key IDs, broker audience and environment. Owner signing keys are never sent to the broker or model.
4. `/execute` rechecks the node signature and owner signature, action, scope and expiration. It requires a separate audit sink's **signed intent acknowledgment**, rechecks the owner session and MFA gate after the audit hop, then calls the v0.4 atomic canary RPC. The database candidate rechecks time, trusted key IDs, trust gate, stored proposal and unique owner/nonce in one transaction.
5. After an effect, the broker asks the audit sink to append a signed result. Missing result acknowledgments produce `EXECUTED_AUDIT_PENDING`; uncertain database outcomes produce `EXECUTION_OUTCOME_UNKNOWN_DO_NOT_RETRY`. Neither state authorizes retrying the effect. `observer.mjs` can construct a signed statement from an independently supplied read-only source; `reconcile.mjs` checks it and can recover a missing result audit entry without retrying the effect. These components do not themselves provision an independent host or source.

The protocol never treats matching hashes, a local test, an audit log entry or a signature alone as proof of an external effect, operator independence or actual provider inference.

## Included components

- `core.mjs`, `http.mjs`: authenticated, strictly shaped proposal and execution handling; compact JSON rejects duplicate-member ambiguity.
- `adapters.mjs`: Supabase Auth / existing v0.3 key and proposal RPC adapters plus a **v0.4-only** execution RPC adapter; HTTPS audit client. No fallback to the old execution RPC.
- `owner-approve.mjs`, `proposal-client.mjs`: independent owner signing on a trusted terminal and host-controlled node signing.
- `audit-ledger.mjs`, `audit-http.mjs`, `audit-main.mjs`: a separate single-writer, fsync-backed, signed, idempotent local audit process; a loopback HTTP service for a separately configured TLS boundary. Each record signs its sequence, predecessor and acknowledgement hash. The authenticated `/head` endpoint exports a signed checkpoint; when a separately retained checkpoint is supplied through `SAC_AUDIT_ANCHOR_PATH`, startup verifies the anchored prefix. The log is not immutable, no off-host anchor storage is provisioned, and deletions after the latest saved checkpoint remain undetectable.
- `audit-witness.mjs`, `audit-witness-client.mjs`, `witness-main.mjs`: a separate-process checkpoint candidate that validates the complete signed chain and prior head, retains each checkpoint without overwriting an existing file, and requires an independently retained latest head on restart. The optional audit `/snapshot` endpoint requires a distinct reader token that cannot append events. See `AUDIT_WITNESS.md` for deployment and recovery limitations. No witness, immutable store, or external checkpoint is provisioned by this source.
- `observer.mjs`, `reconcile.mjs`: validate the original owner grant and independently supplied execution record, construct and verify a distinct v2 signed observer statement, and support recovery of a missing audit result without effect retry. Trust keys and source must be independently provisioned. The statement binds owner, proposal and signed-grant hash in addition to action and effect. A valid signature establishes an attestation, not the source's factual independence.
- `sql/execute-canary.candidate.sql`: source for the transaction installed by the recorded Supabase migration and exercised in disposable PostgreSQL CI. It grants no runtime role; the installation is locked and does not independently verify signatures. The historical source header predates its installation.
- `worker/`: candidate rootless, offline, resource-limited triage wrapper with pinned image and explicit seccomp profile requirements. It opens intake path components without following symlinks, rejects hardlinked or changing files, and mounts a private read-only snapshot. The v0.4 entry point returns a nonzero process status for rejected files; exit zero indicates only an advisory report, not that a file is safe. The underlying v0.3 scanner remains advisory and does not render or sanitize documents. An ephemeral CI host exercised the rootless wrapper using a deliberately incomplete test profile; the production host and profile remain unqualified. The intake root and staging process require trusted host ownership.

Consult that workflow's job logs for results; neither test proves production infrastructure qualification.

**Wire and ledger compatibility:** the reconciler now requires `sac.effect-observation.v2` and its v2 signature domain, including `owner_id`, `proposal_id`, and `grant_sha256`; it rejects the weaker v1 observation. Newly written audit records include `chain_signature_b64url`. Old ledgers without it fail closed and must be retained separately for review; no automatic rewriting or migration is provided.

## Endpoint contracts

Run `broker-main.mjs` on an authorized trusted host after explicit provisioning. It binds loopback only; a separately managed ingress supplies TLS and network controls. `POST /propose` accepts compact JSON with exactly `action`, `node_kid`, and `node_signature_b64url`. After owner review, `POST /execute` requires those fields plus `proposal_id`, `grant`, `owner_kid`, and `grant_signature_b64url`. The caller passes its user JWT as `Authorization: Bearer <user-jwt>`; authentication is checked server-side. Neither the API nor the supplied client generates an owner approval.

For owner review, the owner supplies a compact JSON file containing exactly `action`, `action_digest`, `proposal_id`, `node_kid`, and `node_signature_b64url`; its trusted local configuration must point to independently provisioned owner and node public JWK files. `owner-approve.mjs` rejects non-interactive use and loads the owner private key only after the terminal confirmation. Audit/observer public keys and source allowlists used by `reconcile.mjs` must come from a **separate** owner-controlled file; never trust keys included in model-provided evidence.

Host configuration is explicit through `SAC_SUPABASE_ORIGIN`, `SAC_SUPABASE_ANON_KEY`, `SAC_SUPABASE_SERVICE_KEY_PATH`, `SAC_AUDIT_ORIGIN`, `SAC_AUDIT_TOKEN_PATH`, `SAC_AUDIT_SINK_ID`, `SAC_AUDIT_PUBLIC_JWK_PATH`, `SAC_BROKER_AUDIENCE` and `SAC_BROKER_ENVIRONMENT`. Secret files must be absolute, regular, single-link, owner-owned, and inaccessible to group/other users. The audit process has its own `SAC_AUDIT_DIR`, `SAC_AUDIT_PRIVATE_KEY_PATH`, and `SAC_AUDIT_TOKEN_PATH`. Configure distinct process identities, secrets and storage; the example alone does not establish separation.

## Release gates and limits

- The v0.4 RPC candidate grants no runtime caller execute permission and explicitly revokes `service_role` as well as `PUBLIC`, `anon` and `authenticated`: Supabase's default function privileges can otherwise grant it automatically. An installation must verify the actual database and migration record; source alone is not evidence of installation. Existing v0.3 behavior, including its edge-only time/key checks, remains unchanged until separately reviewed and migrated.
- Transactional expiry and key-row rechecks were exercised in disposable PostgreSQL CI. The candidate takes an advisory per-node admission lock, but production quarantine/revocation writers must adopt the same lock and be tested for concurrent races. A check immediately before transaction return does not guarantee a commit-time wall-clock deadline.
- The current gateway uses a privileged service credential in its trusted process. Private-file controls reduce accidental exposure but do not provide least-privilege roles, a hardware security module, or isolation against a compromised broker. The existing owner-session gate is queried before proposal and before execution, then rechecked after the audit hop; actual owner MFA, session revocation and the remaining race between the last gate and transaction commit are not verified.
- Live readback also found that `service_role` can call the old v0.3 security-definer execution function and insert into broker execution, proposal and spent-grant tables. A new narrow v0.4 role alone would not close those paths. Inventory dependent callers and replace or retire the legacy path, revoke the broad rights in a tested coordinated migration, and verify that direct SQL, both old and new RPCs, and inherited/default role grants cannot bypass admission before activating keys.
- The SQL candidate uses `SECURITY INVOKER`; making it executable would require its caller to hold direct rights on the underlying tables. Those rights could bypass the intended function, so the candidate is **not a production authorization boundary**. Redesign and independently review database-side privilege separation and signature admission before granting execution or enabling effects.
- The audit process has a separate key and durable local log, but no external append-only or WORM sink, no provisioned external checkpoint storage, no multi-writer durability, and no independently operated observer. A signed head helps only when a trustworthy separate operator retains and restores the latest checkpoint; stale or missing checkpoints cannot detect all deletion. A crash may leave a lock requiring deliberate operator recovery. Audit-result failure after an effect must be reconciled without resubmitting the grant.
- Actual rootless container execution, hostile-document tests, egress denial, credential boundaries, distributed replay races, backups, external reconciliation, owner enrollment, and controlled live-model evaluation remain required. The model provider, production configuration and existing quarantine state are unchanged by these source files.
