# Empty legacy broker lockdown

`sql/lock-empty-legacy.candidate.sql` is a targeted, transactional revocation candidate. It takes table locks before checking that all six v0.3 broker tables contain zero rows. It refuses to continue if any owner/node key, proposal, spent grant, execution or audit evidence exists. It revokes API-role execution of the old v0.3 effect RPC and direct API-role writes to those tables, then checks effective table and column privileges for API roles and every role they can assume. If a verification fails, the transaction rolls back. It leaves table reads and the v0.3 key-lookup and proposal RPCs unchanged.

If applied, calls to the old effect RPC through `service_role` will fail with a permission error. The proposal RPC is a security-definer function and can still write proposals; direct-table revocation does not eliminate this indirect write. The installed v0.4 function remains locked. This change alone does not authorize a new effect path, isolate the service key, enroll an owner, or establish production readiness.

The test fixture models the relevant default function and table grants, verifies the nonempty guard, a concurrent insert before lock acquisition, inherited table and column privileges, an assumable non-inherited role, transactional rollback, preservation of read access, and denial of the old effect RPC and direct writes. It is not the live project or a full reconstruction of the old function's security-definer behavior.

This transaction was applied to the connected live project on 2026-11-15; see `LIVE_INSTALL_2026-11-15.md` for the migration, exact SQL hash and readback. Its historical SQL source header predates installation. The transaction is not a generic migration for other projects: inspect the destination's ACLs and dependent callers and review the effect before applying it elsewhere. Empty broker tables and query statistics do not prove that no external clients depend on permission-denial behavior. If a rollback is deliberately required, restore only the previously observed specific grants after reviewing the resulting bypass; restoring the v0.3 effect RPC or direct write grants reopens the original risk. Never activate broker keys simply because these revocations succeeded.
